## 1. Purpose

This report documents the provider fallback model strategy.

The project primarily uses an LLM-based generator. In production, LLM providers may fail due to timeout, quota limits, transient network errors, or provider-side incidents.

Before this optimization, a generation failure would be handled by the error handling framework and return `SYSTEM_ERROR`.

This optimization adds a recovery layer before the final error fallback:

    primary LLM generator fails
    -> fallback to extractive generator
    -> return a grounded answer from retrieved chunks
    -> record fallback metadata in runtime logs

## 3. Runtime Behavior

### Normal path

If the primary LLM succeeds:

    fallback_applied = false
    final_generator_type = llm

### Fallback path

If the primary LLM fails and fallback is enabled:

    fallback_applied = true
    fallback_reason = primary_generation_error
    primary_generator_type = llm
    fallback_generator_type = extractive
    final_generator_type = extractive

### Final error path

If retrieval fails, or generation/fallback fails in a way that cannot recover, the existing error handling framework returns:

    refused = true
    refusal_reason = SYSTEM_ERROR

## 4. Evaluation Method

The fallback evaluation validates two cases:

1. fallback generator is configured
2. simulated primary LLM failure falls back to extractive generation

The second case monkeypatches the primary generator to raise:

    RuntimeError("simulated primary LLM failure")

Expected behavior:

- HTTP status remains 200
- response is not refused
- answer is generated by the extractive fallback
- runtime log records `fallback_applied = true`
- runtime log records `fallback_reason = primary_generation_error`
- runtime log records primary/fallback/final generator types

## 7. Production Impact

This optimization improves generation-stage availability.

The service can now recover from transient primary LLM failures by using an extractive fallback answer grounded in retrieved chunks.

This provides a stronger production behavior than immediately returning `SYSTEM_ERROR`.

It also improves observability by recording fallback metadata in structured runtime logs.

---

## 8. Limitations

Current limitations:

- The fallback generator is extractive, not a second LLM provider.
- Fallback answer quality may be lower than LLM-generated answers.
- There is no retry/backoff before fallback.
- There is no provider health check.
- There is no circuit breaker.
- There is no multi-provider routing strategy.
- Fallback is currently applied only at generation time.

---

## 9. Future Work
